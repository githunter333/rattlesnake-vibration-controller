1a  GOLDEN-OUTPUT TEST                                                  [done]
--------------------------------------------------------------------------------
control_laws/tests/golden_optdiag.py runs fixed closed-loop scenarios on the frame
plants (6x8, 10x14, 10x14 rank-deficient) with seeded measurement noise and compares
each cycle's drive CPSD with a recording.  The laws use no random numbers and repeat
bit for bit, so the check is exact first (a hash per cycle) and numeric second
(--rtol / --atol-db).  --strict demands bit-identical output.  --law-dir tests a
copy of the laws, which is how every mutation check below was done.

  * Scenarios ended at 20, then 30 (named twins, 1b), then 43 (below).

1b  NAMED PARAMETERS                                                    [done]
--------------------------------------------------------------------------------
Before: three laws each parsed the same comma string by position, with defaults
repeated in code, docstrings and comments, and any bad value silently dropped every
later field.

Now: one parameter table per law (name, default, conversion, legacy position),
one parser, one place for defaults.
  * Named form:  one "name: value" per line (or separated by ;), # comments,
    case-insensitive, empty value = default, e.g.
        max_bins_per_update: 10
        max_drive_coherence: 0.8
    A misspelled or unknown name, or an unreadable value, stops the test with a
    message that names the line and the nearest valid name, e.g.
        unknown parameter 'rgu' (did you mean 'reg'?)
    (Rattlesnake catches constructor exceptions and shows them in an error dialog.)
  * Legacy comma strings parse exactly as before; all 14 distinct archived-profile
    strings (15 law-and-string pairs across 46 workbooks) are in the test set.  One deliberate change: a field that cannot be read keeps
    its default with a warning and the later fields are still read.
  * The octave law's collision is fixed for the named form.  Its five parameters
    shared positions 6-10 with the base class, so a legacy string such as
    "...,5,0,6,100,1000" also set error_domain 'db' and 100 IRLS passes.  Measured:
    that made the law about 60x slower (18 s vs 0.3 s over three cycles on 6x8).
    Legacy strings still behave that way so archived runs reproduce, and now print a
    warning.
  * Generated reference: control_laws/optimal_diagonal_parameters.md (name, field
    number, default, meaning), produced from the tables by tests/make_parameter_
    reference.py; a test fails if it goes stale.  The old docstring said
    frf_update_threshold defaulted to 0.05; it has been 0.5 since 2026-09-19.

Proof:

1e  CONSISTENCY                                                         [done]
--------------------------------------------------------------------------------
Three items on your list; one was a real inconsistency, one was already fine, one was
missing guidance.

  * Coherence measure.  The laws cap the MAGNITUDE |X_ij|/sqrt(X_ii X_jj) of a pair of
    drives (the SDP constraint, the shared cap helper and the fast law's guard all do),
    but compare_optdiag.py and compare_optdiag_frame.py reported the SQUARE under the
    plain name, so a law sitting exactly on its 0.95 cap printed 0.90 against it.  Now
    "drive coherence" means the magnitude everywhere; the squared measure is always
    called coherence squared (gamma^2).  Defined once in the base law's docstring, said
    in the parameter description and the cap helper, and the two comparison scripts
    report the magnitude (their old numbers are the squares of the new ones, e.g. the
    0.19 / 0.30 gamma^2 medians in your Oct 30-31 table read about 0.44 / 0.55 now).
    tests/check_coherence_measure.py pins it, including a run of the SDP law on a real
    plant with a cap of 0.5 (it stays under and reaches it); both mutations tried were
    caught.
  * Parameter doc.  Mostly settled by 1b's generated reference.  The remaining risk was
    docstring prose quoting a default that the table has since changed (it had: 0.05 vs
    0.5 for frf_update_threshold).  check_named_params.py now compares every "default X"
    in the three docstrings with the tables.  None had drifted; changing one in a copy
    makes the check name it.
  * Time-budget default.  Already consistent: 0 (off) in the code, the docstrings and the
    reference.  Left at 0, because every behaviour change in these laws ships off by
    default and archived profiles must reproduce.  What was missing was the guidance:
    at 10 drives x 14 controls the default 20 lines per call can exceed a 1 s control
    cycle (worst call 1.1-1.5 s).  The generated reference now has a "Choosing the time
    budget" section.  The numbers were re-measured today with compare_optdiag_frame.py:
    the errors (SDP 0.12 dB, fast 0.23 dB) and the fast law's line counts reproduce your
    notes; times and the budgeted SDP row (0.63 dB, 109 lines today; 0.34 dB, 148 lines in
    your notes) depend on the machine.  Whether the DEFAULT should change (say to 500 ms
    for the fast law) is a policy call that is yours; the code is ready for either.

No logic changed: the syntax trees of the laws and control_laws.py, ignoring docstrings
and Param descriptions, are identical to the commit before; all 43 golden scenarios are
bit-identical under --strict.  (8daaa0a2)
