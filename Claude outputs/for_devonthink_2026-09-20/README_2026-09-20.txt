WHAT CHANGED, AND WHY YOU SHOULD NOT TRUST THE 09-15 PAIR ON THESE POINTS
-------------------------------------------------------------------------
1. Runs 05 and 06 are labelled optimal_diagonal_control_fast in the 09-15 report.
   They ran the base class. The fast law's demotion gate was bitwise equality, and
   with the FRF update on -- which is how all twelve runs were taken -- the array was
   never bit-identical, so every bin fell through to the SDP. The real fast-law
   measurement is in section 3 of the new comparison report.

2. Both optimal-diagonal laws are classified as feedback laws in the 09-15 report.
   They are open loop: they refine against their own predicted response and never
   read the measured one. Corrected 2026-09-17.

NEW SINCE 09-15

 * The fast law measured properly, and the realizability failure that made run 22

 * drive_rcond, and why the threshold is now a multiple of the plant's own
   singular-value spread rather than an absolute ratio.

REVISION 2026-09-21
-------------------
Both documents were rebuilt on 2026-09-21. Filenames are unchanged, so these
replace the copies of the day before rather than sitting beside them.

What changed:

1. THE LOOP CLASSIFICATION, corrected a second time. The 2026-09-15 report
   called the optimal-diagonal laws feedback laws; the 2026-09-17 correction
   called them open loop, which over-shot. They are closed on the identified
   plant model -- they re-solve against the live FRF every cycle, which is
   what runs 29/31/32 were about -- and open on the response error. The
   comparison report's "loop" column now reads model / error / none instead
   of open / feedback, and section 2 carries the full note. No measured
   result changed; only the label.

2. A NEW SECTION 7 in the comparison report, and a new subsection plus a
   tenth flow chart in the reference, covering the response-error trim added
   2026-09-21. It closes the open half of the loop. Off by default, four
   offline tests passing, NOT YET RUN ON THE RIG.

Sections 7 and 8 of the comparison report are renumbered 8 and 9.


REVISION 2026-09-21, SECOND PASS
--------------------------------
Rebuilt again the same day, after run 35. Filenames unchanged, so these
replace the earlier copies rather than sitting beside them.

3. RUN 35 SCORED AND ADDED. optimal_diagonal_control_fast with the trim
   present in the code but off. It passed every pre-registered band and is
   now the fourth point in the FRF-update sequence in section 4 of the
   comparison report. Its regression value: zero occurrences of either trim
   log line in a full run, so the trim is provably asleep inside the
   framework, not only in an offline harness.

4. THE MODEL-MISMATCH MEASUREMENT. Reconstructing the law's own per-bin
   prediction from run 35's saved FRF and drive and comparing it with the
   measured response gives a mismatch of 0.060 dB rms over 7208 in-band
   channel-bins. There is essentially no model error on this plant: the
   FRF-update loop already does the whole job, and the residual 6.0 dB rms
   is the law's own optimisation limit. First time the self-consistency
   diagnostic has been checked against measurement rather than trusted.

5. THE TRIM'S GATE NOW HAS ITS OWN THRESHOLD, response_trim_gate_db,
   default 0.5 (parameter field 15). It had reused error_threshold_db at
   1.0 dB, which run 35's data showed would have had the trim integrating
   the solver's own sub-threshold shortfall -- thirteen times larger than
   the model error it exists to correct. Documented in section 7 of the
   comparison report, in section 2 of the reference, in the tenth flow
   chart, and in the parameter table.

Both documents now say plainly that the trim has been half-tested: the
default path is confirmed on hardware, the gain has never been on, and on
this plant there is too little model error for run 36 to show much. That is
a limitation of the plant, not of the loop, and the documents say which.
