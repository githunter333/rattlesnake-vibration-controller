1. WHY THE FAST LAW WAS RAGGED -- THE SOLUTION WAS UNREALIZABLE, NOT WRONG
===============================================================================
The unconstrained Burer-Monteiro solve puts drive energy in near-null directions of H.
The predicted response then depends on inter-drive cancellation the rig cannot reproduce:
the answer is correct for the model and wrong for the hardware.

Measured offline by perturbing the commanded drive 1 %:

  configuration                   rms    level    rms +1%   level +1%
  factored, unconstrained        4.64    -0.42     11.85    +16.69
  factored + drive_rcond 1e-2    3.73    +1.94      4.68     +3.80
  SDP + coherence cap 0.95       4.16    -0.50      7.23     +7.92
  SDP, cap off                   4.09    -0.49      7.98     +9.09

A 1 % drive perturbation predicted +16.69 dB.  Run 22 on the rig measured +14.29 dB at
17.84 V peak.  That is the prediction landing, and it is the whole explanation for the
ragged control.

MY ERROR, for the record: drive_rcond had been gated to dB error domain only, leaving the
factored path unconstrained in its DEFAULT linear mode.  Run 22 was the consequence.
Fixed in 6970a717 (18:20) -- drive_rcond now applies in BOTH error domains.  This was the
user's option 3 ("its ok to make drive_rcond apply in linear mode if that is feasible")
and it turned out to be the whole fix; options 1 (soft coherence penalty) and 2 (dither +
FRF update) were not needed and option 2 remains untried.

===============================================================================
3. MAKING THE THRESHOLD AUTOMATIC -- bbb9aa02
===============================================================================
drive_rcond is now expressed as a MULTIPLE of the plant's own singular-value spread
(default 2.0; a negative value is read as an absolute ratio, so the old numbers still
work).  _effective_drive_rcond measures the spread from H itself, with gap detection to
find the structural floor rather than the identification noise floor.

In-band median sigma_k/sigma_1 on this plant: 1.0000  0.3189  0.0844  0.0324  0.0152
0.0017.  sigma6 is the noise floor -- the plant is rank 5, not 6.  sigma5/sigma1 = 0.0152
is the smallest structural direction, and 2.0 x that is 3.0e-2, the swept answer.

Two bugs found and fixed while building this, both worth remembering because the same
mistake appears again in section 5:
  - The spread was measured over ALL lines, giving 0.1435 instead of 0.0152 -- a factor of
    9.  Out-of-band lines have no excitation and their singular values are noise.  Fixed
    by masking to in-band bins.
  - Scaling off sigma_min instead of sigma5 gave a required multiple of 18 instead of 2.
    Fixed by gap detection.
  - A single-bin fallback plus a permanent cache made an offline harness report 10.34 dB
    for a configuration the control loop scores at 5.95.  Fixed; no caching until H_cache
    is populated.

Runs 26 and 27 confirmed it: the law derived 0.0302 from run 26's identification and
0.0303 from run 27's, without being told, and run 27 reproduced hand-tuned run 24 on
every accuracy measure.  Verified to 1-2 % across five separate system IDs.

5. FRF UPDATE ON -- RUN 28, AND THE BUG IT EXPOSED
===============================================================================
Offline first, solving on H and running on a perturbed plant (rms dB / level dB):

  configuration                   exact        H off 2%      H off 5%      H off 10%
  factored, unconstrained      4.52 / -0.39  4.63 / +4.06  8.95 /+10.57  13.72 /+16.23
  factored + auto drive_rcond  5.90 / -0.74  4.33 / -0.56  3.78 / +0.23   4.13 / +2.25
  SDP + coherence cap          4.05 / -0.50  3.56 / +0.80  5.11 / +4.68   8.61 / +9.55

The restricted factored path is the MOST FRF-robust of the three: slightly worse with an
exact model, clearly better with a wrong one.  drive_rcond was added for drive-realization
error and handles model error at least as well, and better than the coherence cap does.

That undercuts the demotion gate's premise.  The gate demotes to the SDP whenever H moves
more than frf_update_threshold, but at 5 % model error the restricted factored path beats
the SDP, so demoting trades a better solver for a worse one and pays 18x the time for it.

Run 28 (probe, FRF update on, threshold 0.05) then measured the gate over 549 calls:

  median 4.3736, 90th 6.2169, max 179.6692, demoted 99 %

A 437 % change in the FRF every cycle is not physical.  The base class's own drift metric,
which looks only at refined (in-band) bins, read median 0.1705 on the same data.  A factor
of 25 between two measurements of the same quantity.

CAUSE: _h_moved compared live H against cached H over the whole 2049-bin array.  1148 of
those bins are out of band -- no drive energy, so the live H1 estimate is noise and its
relative change per cycle is enormous.  The gate was responding to out-of-band noise and
never to the plant.  Exactly the same mistake as measuring the singular-value spread over
all lines (section 3), in a different function.

Because the gate tripped on essentially every call, optimal_diagonal_control_fast was
byte-for-byte the base class whenever the FRF update was on -- which is the same failure
the relative-change threshold was introduced on 09-17 to fix, reintroduced through the
measurement instead of through the comparison.

SECOND EFFECT, same parameter: frf_update_threshold also sets the base class's drift
budget (optimal_diagonal_control.py:465,473).  At 0.05 nearly every previously-refined bin
counted as drifted, so 10 of the 20 bins per cycle went to re-solving old bins forever --
run 28 reached cum_frf_updates = 5570 and climbing.  Half the refinement budget, spent
permanently on noise.

FIX (written, staged, NOT COMMITTED -- see section 7): _h_moved now restricts both arrays
to in-band bins before taking the norms, and logs the running distribution (median, 90th,
max, demotion rate) on every trip and every 25th call.  That logging matters because only
the FINAL FRF is saved in a run file, so a saved run shows cumulative drift (about 28 %
between system ID and end of control on run 21) and says nothing about the per-cycle
movement the gate actually tests.

Checked that this does not show up when comparing two system-ID FRFs: runs 26 and 27
differ by 0.1033 measured either way.  A system ID excites the whole band, so the
discrepancy only appears with the live control-phase estimate.

9. RETRACTIONS STANDING FROM THIS WORK
===============================================================================
Kept here because each was stated confidently before being checked, and the findings
document carries them too.
  - The damping-sensitivity analysis (0.089 -> 0.153, "use 5e-2").  The analytic FRF I
    rebuilt from M/K/C produced no near-zero sigma6, which is inconsistent with the
    rank-5 structure the measured plant shows.  Those numbers must not be used.
  - "Run 13 had a weak system ID" (retracted 09-17, repeated here because it still gets
    quoted).  I compared run 13's channel-7 minimum against other runs' non-channel-7
    minima.  Channel 7 reads 0.28-0.54 on all thirteen identifications; it is a property
    of the rig.  Scored like against like, run 13's ID was the best of the set.
  - "1.37 dB is model error."  The control-phase FRF predicting its own data to 0.06 dB
    is near-tautological -- it is an H1 estimate fit to that very drive.
