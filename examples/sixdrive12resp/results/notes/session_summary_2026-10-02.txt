--------------------------------------------------------------------------------
WHY THE STRING IS HARD TO READ
--------------------------------------------------------------------------------
extra_parameters is fifteen positional comma-separated fields with no names,
truncatable only from the right.  To set field 10 you must supply fields 1-9
even if you only want their defaults, and a string that fails to parse is
discarded silently with every default left standing.

Three things beyond that:

1. FIELD 6 IS A HOLE IN THE BASE CLASS.  bm_rank is the Burer-Monteiro
   factorisation rank and only the fast variant has a factored path.  The base
   parser steps over index 5 entirely -- it goes from parts[4] straight to
   parts[6].  One parameter format serves both classes, so a base-law profile
   still has to put a placeholder in field 6 to reach field 7.  Every committed
   base-law profile puts "6" there, where it does nothing at all.

2. FIELD 10 IS PARSED BY THE BASE CLASS AND USED ONLY BY THE FAST ONE.
   drive_rcond is inert on optimal_diagonal whatever it is set to.  Run 16 set
   it to 1e-2 on the base law and it did nothing.

3. FIELD 2 DOES TWO JOBS IN THE FAST LAW, AND ITS SCALE CHANGED.  In both
   classes frf_update_threshold is the refinement scheduler's drift threshold.
   In the fast class it ALSO gates demotion to the base solver -- one number,
   two decisions, which do not obviously want the same value.  And the number is
   not comparable across the gate repair: 0.05 was set against the old
   all-bins metric, 0.5 against the repaired in-band one.  Base-law profiles
   carry 0.05 and fast-law profiles carry 0.5; that is not a tuning decision,
   it straddles a metric change.

--------------------------------------------------------------------------------
THE LIVE TRAP -- drive_rcond CHANGED MEANING AND SIX PROFILES PREDATE IT
--------------------------------------------------------------------------------
The sign of field 10 is now a mode switch.  Positive is a MULTIPLE of the
plant's smallest structural singular-value ratio; negative is an ABSOLUTE ratio,
|value|.  The default is 2.0, because this frame's smallest structural direction
is sigma_5/sigma_1 = 0.0152 and 2.0 x that is 0.0304 -- the 3e-2 the runs 22-25
sweep found as a genuine minimum.  Expressed as a multiple it tracks a
differently conditioned article without re-tuning, which was the point.

Profiles written before the change hold drive_rcond as a positive ABSOLUTE
ratio, and today's code reads those same numbers as multiples:

    profile                      field 10   meant      now reads as
    -------------------------------------------------------------------
    profile_15_optdiagfast_db      1e-2     1.0e-2     1.5e-4
    profile_16_optdiag_db          1e-2     1.0e-2     inert, base law
    profile_17_optdiagfast_db      3e-3     3.0e-3     4.6e-5
    profile_18_optdiagfast_db      1e-2     1.0e-2     1.5e-4
    profile_24_optdiagfast_rcond   3e-2     3.0e-2     4.6e-4
    profile_25_optdiagfast_rcond   5e-2     5.0e-2     7.6e-4
    _superseded_profile_17         1e-3     1.0e-3     1.5e-5

Every one is now small enough that the restriction effectively does not apply.
That is run 22's configuration, the deliberate failure case: 9.91 dB rms, 52.9%
of lines out, +14.29 dB level, 859 V^2, because the unconstrained solution is
unrealisable rather than wrong.  Anyone re-running profile_24 today would get
run 22's result and have no reason to suspect why.

--------------------------------------------------------------------------------
A CORRECTION TO THE 10-01 MODIFICATION REGISTER
--------------------------------------------------------------------------------
Section A2 said the drive-coherence cap defaults to 1.0, i.e. OFF, in every law.
That is wrong for three of the six:

    match_trace_pseudoinverse, buzz, pseudoinverse      default 1.0   OFF
    optimal_diagonal, optimal_diagonal_fast,
    diagonal_congruence                                 default 0.95  ON

On those three, omitting the field leaves the cap ON.  "Cap off" has to be asked
for explicitly, which is what profile_04_optdiag_capoff does by passing 1.0.
The register's summary row has been split and the section rewritten, and it now
points at the new parameter reference.

The cap costs this law +0.02 dB, so 0.95 is the right default -- the error was
in the documentation, not the code.  But it is exactly the kind of thing a
reader takes from a register without re-checking, which is why it is called out
rather than quietly fixed.
