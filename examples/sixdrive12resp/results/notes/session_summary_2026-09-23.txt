1.  THE LOOP CLASSIFICATION, CORRECTED A SECOND TIME
----------------------------------------------------
Reports before 2026-09-17 called optimal_diagonal_control a feedback law.  The
correction made then called it open loop.  Both are wrong.  Two separate loops:

  CLOSED on the identified plant model.  control() and system_id_update() hand
  the live FRF to _refine_batch every cycle.  Step 1 re-solves bins whose H
  moved past the gate; step 3 re-solves bins whose predicted error degraded
  against the CURRENT H, which is what catches a plant that softens with level
  while drifting under the gate.  Runs 29/31/32: 17.03/18.44/16.22 V^2 with
  the update on against 153/485/245 with it off.

  OPEN on the response error.  The objective is the PREDICTED response
  diag(H X H^H); last_response_cpsd was accepted and never read.

The report's loop column now reads model / error / none instead of
open / feedback.  No measured result changed, only the label.
compute_report_data.py was deriving that column from an OPEN_LOOP set and
would have silently reverted the relabel on the next assemble, since
report_data.json is rebuilt from .floor_cache; fixed at source, and it now
returns 'model+error' when a parameter string carries a live trim gain.


2.  THE RESPONSE-ERROR TRIM (optimal_diagonal_control, fields 11-15)
--------------------------------------------------------------------
_update_response_trim closes the open half: a per-bin, per-channel
multiplicative correction on the solver's target.  OFF by default.

Two design choices carry it, both settled on paper before any code:

  WHAT IT INTEGRATES.  Not measured-vs-predicted, which is the obvious choice
  and is wrong: for a constant multiplicative bias b it reads 10log10(b) for
  ever whatever the trim does, because shrinking the target shrinks prediction
  and measurement together.  It is a mismatch READOUT, not an error, and an
  integrator driven by it runs to its clamp and stops.  It integrates
  measured-vs-SPECIFICATION, which drives to zero.

  THE SOLVER-AGREEMENT GATE.  Integrating that alone winds up at every bin the
  plant cannot reach -- this frame is rank 5 with six drives.  The trim is
  applied only where the solver reached what it aimed at.  A shortfall the
  solver itself predicted is an achievability limit, not model error.

Speed: the COMMON part of each bin's change is applied straight to the stored
drive CPSD, since scaling X by a positive scalar scales diag(H X H^H) by
exactly that scalar and leaves coherence and rank untouched.  Only the
per-channel shape waits for the scheduler.

Also fixed while there: octave_band_switching_control overrode
set_test_level_db without chaining, so the base class's trim freeze could
never have armed on that subclass.

4.  match_trace_pseudoinverse -- A WORKING FRF UPDATE PATH
-----------------------------------------------------------
With "Update Transfer Function During Control" on, this law read the FRF once,
in the cycle-1 pseudoinverse, and never again.  refresh_shape (field 4) closed
that in September but only by re-solving every line every cycle, which on an
already-averaged FRF means re-solving on noise.

New: field 5 refresh_threshold (per-line gate, change since that LINE's last
solve -- not since the previous cycle, which can never see slow monotonic
drift), field 6 frf_diag (instrumentation).  Both default to previous
behaviour; an archived two-field string is bit-identical to the parent commit
over five closed-loop cycles.

THE GATE MEASURES SHAPE, NOT MAGNITUDE, and that came from a test, not from
reasoning.  Refreshing lines whose H had drifted by a pure per-line GAIN moved
the command by 7e-11 -- i.e. not at all, because trace_ratio is per line and
already absorbs a per-line gain change exactly.  An un-normalised gate would
fire on every such line and buy nothing.  The metric now normalises each line
by its own Frobenius norm first.

UNREFRESHED LINES ARE BIT-EXACT.  The first implementation used a NaN sentinel
and let them through a multiply-by-1.0 the no-refresh path does not do.  That
cost one ulp on one line at cycle 2, which the closed loop grew to 1.7e-11 by
cycle 4.  Level-setting is now restricted to refreshed lines by sub-array.

7.  RANK BY SINGULAR-VALUE GAP (rcond takes a sign)
----------------------------------------------------
Run 39 exposed why the drive behaviour was unstable to begin with:

                   median sigma_k/sigma_1                  sigma_6
    system ID  [1, 0.319, 0.085, 0.032, 0.015, 0.0017]     0.00167
    converged  [1, 0.314, 0.084, 0.032, 0.015, 0.00014]    0.00014

sigma_6 is inflated by estimation noise at system ID (20 averages) and
collapses by twelve once averaged.  rcond = 1e-3 sits BETWEEN the two, so the
same threshold keeps six directions on 72% of in-band lines from the
system-ID estimate and five on 90% from the converged one -- agreement 24.5%.
The law's rank was a readout of estimator quality.  Run 40 reached rank 5 by
luck.

That is also the origin of the startup solve's oddity: drives 5 and 6 at
40-90x the power of drives 1-4, 98.6% coherent and ~115 degrees apart -- a
large nearly-cancelling pair poured into a direction that does not exist.
And why match_trace commands the most drive on the board.

rcond now takes a sign.  Positive is the absolute ratio, unchanged, every
archived run bit-identical.  Negative selects rank at the largest believable
gap with |rcond| as the protect threshold.  Over four saved FRFs:

    absolute rcond 1e-3         24.5% agreement   modal rank 6/5/5/6
    gap, unrestricted           80.0%             5 on all four
    gap, protect 0.05, min 3    88.7%             5 on all four
    gap, protect 0.03, min 2    89.3%             5 on all four

Two guards, both found by measurement: unrestricted gap detection picks rank 1
or 2 on a quarter of system-ID lines, because at a resonance sigma_1 dominates
and the largest gap is at the TOP of the spectrum.  So a direction above
`protect` is never discarded, and a gap must exceed 3x to be believed.
Constants sit on a flat plateau, one step conservative of the peak.

NOT YET RUN ON THE RIG.  The residual 11% -- rank 2 on 8-10% of lines in both
estimates -- is consistent between estimates but unexplained.  Consistent is
not correct.


8.  THE NONLINEAR PLANT -- BLOCKED, AND WHY
--------------------------------------------
Run 42 set up on sdynpy_frame6x12_system_nonlinear.npz (Hardware Type 7, not
6).  Hardware confirmed engaged: n_modes=1, strength=1, k3=-5.6e11, c2=240.
System ID saved.  STOPPED BEFORE THE CONTROL RUN.

The nonlinearity is a softening cubic plus quadratic damping on ONE mode
(120 Hz, zeta 0.040), calibrated to -4% frequency and x1.20 damping at twice a
modal amplitude q0_ref corresponding to 20 V RMS of MODE-SHAPED drive.

Computed from the system model and run 40's actual commanded drive:

    commanded drive            13.499 V rms
    modal amplitude q_rms      1.64e-06
    q_rms / q0_ref             0.0067

    strength    1  ->  frequency shift  -0.0000 %
    strength   25  ->  -0.0011 %
    strength  100  ->  -0.0045 %
    strength  400  ->  -0.0178 %

The drive is respectable but only a tiny fraction lands on that one mode --
broadband random over 100-1000 Hz projected onto a single mode shape -- and
the shift goes as amplitude SQUARED.  Reaching a few percent would need
strength of order 1e5, far outside the calibration, where the Duffing term
would stop behaving like the calibrated model.

CAVEAT ON THAT NUMBER: it assumes 1 V of drive = 1 N at the drive DOF.  The
hardware class's voltage-to-force scaling has NOT been verified, and it enters
squared -- at 10 N/V everything above improves by 100x.  Worth checking before
treating this as settled.

DECISION: move to sdynpy_frame6x12_system_nonlinear_allmodes.npz, which
spreads the nonlinearity across every mode so the whole drive contributes
instead of one mode's projection.  Already built and in the tree.
sdynpy_frame6x12_system_shifted.npz -- two fixed FRF states rather than
amplitude dependence -- is the cruder fallback that guarantees a known shape
change.

THE TRAP, which cost all four runs and which I did not see until run 44 had
already failed:

    shift  ~ (3/8)|k3| A^2 / wn^2      rises linearly with |k3|
    q_esc  =  wn / sqrt(|k3|)          falls as 1/sqrt(|k3|)

so the frequency shift available AT escape is 3/8 = 37.5%, FIXED, whatever k3
is.  Turning up RATTLESNAKE_NONLINEARITY_STRENGTH raises the shift and moves
the cliff toward you at exactly the same rate.  You cannot buy effect with
strength.  With random-drive peaks near 4 sigma the usable shift caps around
2.3%, and with real margin nearer 0.5-1%.  A softening cubic has a FINITE
potential well; the Duffing JUMP criterion (shift/zeta -> 1), which I used to
pick strength 100, never binds -- escape binds first, by a wide margin.

RUN 44  all-modes article, strength 100.  Overflowed in system ID.  k3 reached
-2.55e21.  Strength 25, which I had recommended first, would also have failed
(margin 0.81).  The binding mode was #31 at 837 Hz, where the randomised k3
draw landed at 2.7e18 -- and that mode carries almost none of the shape
change.  A single uniform multiplier cannot serve both.

THE PLANT WAS CALIBRATED THREE TIMES (build_nonlinear_frf_system_escapecal.py):
  1. per-mode reference against the CONTROL drive, MARGIN 6.  Overflowed in
     run 46's system ID.  A flat sysid drive and the shaped control drive
     excite the modes completely differently (per-mode ratios 0.25 to 1.2), so
     referencing one does not bound the other.  Tightest mode had 1.267x on
     4-sigma peaks; the integration starts from rest and the switch-on
     transient ate it.
  2. single global amplitude scale.  Safe and useless -- all the shift lands
     on the one strongest mode, the median LINE barely moves, d_shape 0.0025,
     below the 0.0070 noise floor.
  3. per-mode against the WORST CASE over both drives, MARGIN 10.  Shift
     0.268-0.375% on every mode, margin 2.500 everywhere.  This is the file
     that now exists.

RUN 46 (attempt 3 of the plant, rcond +1e-3) escaped at control cycle 3, at
-12 dB.  Mechanism, and this one the model finally retrodicted correctly:
  - the startup cap deliberately holds cycle 1 NINE dB low;
  - trace_ratio is an unclamped unity-gain integrator with no rate limit, so
    it recovers the whole 9 dB in ONE step (cycle 2 drive ~8x cycle 1 power);
  - rcond = 1e-3 retained the distortion-inflated 6th direction on 97% of
    lines, so the pinv commands enormous drive for little response.
  Together: cycle-2 amplitude 1.09x the calibration amplitude, margin 0.99.
  Predicted escape at cycle 2-3; observed overflow right after drift cycle 3.

RUN 48  same plant, GAP RANK (rcond -0.05).  Margin at cycle 2 went 0.99 ->
3.68.  Ran clean through system ID and 175 control cycles at -18 and -12 dB.
Escaped on the step to 0 dB.

  MY PREDICTION OF 7.5x MARGIN AT 0 dB WAS WRONG.  I scaled run 40's modal
  amplitudes by the ratio of TOTAL drive rms (4.38 V vs 13.50 V = 0.324).
  Projecting run 48's actual drive through the mode shapes instead:

        per-mode q(run48)/q(run40):  min 0.37  median 0.51  MAX 1.47
