-------------------------------------------------------------------------------
WHAT CHANGED IN THE CODE SINCE RUN 13 -- read this before comparing to run 05
-------------------------------------------------------------------------------
a) THE ORIGINAL RATIONALE WAS RIGHT BY ACCIDENT. Runsheet 13 said "with update
   OFF, H is set once at system_id_update() and never re-passed". That is not
   what Rattlesnake does: random_vibration_sys_id_data_analysis.py:431-475
   passes a transfer_function to control() EVERY cycle in both regimes, and
   system_id_update() is never called during control at all. With the update
   off the array simply happens to be the same frozen sysid_frf each cycle, so
   the old bit-equality gate held and the fast path did engage. Right outcome,
   wrong mechanism.

b) THE FAST-PATH GATE NOW USES A THRESHOLD, not bit equality. It demotes to the
   coherence-capped SDP when ||H - H_cache||/||H_cache|| exceeds
   frf_update_threshold (0.05 here). With the update OFF this run is unaffected
   -- H never changes at all. It is recorded because it means run 05 and run 06,
   which had the update ON, were the base SDP law under a different name, and
   are therefore not the "fast" comparison they were taken to be.

c) THE STARTUP LEVEL CAP NOW APPLIES TO THIS LAW, at the -9.0 dB default. Run 05
   and the original run 13 had none. Because the law is open loop the cap binds
   on the FIRST command only -- cycle 2 onward is bit-identical to run 05 -- so
   the converged comparison is unaffected. Practical consequence at the rig:
   the old "RAMP THE TEST LEVEL, this law has no startup cap" warning no longer
   applies. The first command will come in at -9 dB re specification and step
   up on the second.

The law was driven offline with run 01's identification and this exact

      fast  -1.18 dB re spec     SDP  -1.20 dB re spec
      -> the two solves agree to 0.02 dB. The BM path is not trading accuracy
         for speed on this system.

  COVERAGE, and this is the real limit, not solve time:
      901 in-band bins, budget 20 per cycle -> 46 control cycles for ONE pass
      over the band. The fast law spends 149 ms of a roughly 1 s control
      cycle, so the budget, not the solver, is what sets convergence rate
      here. That is the case for raising max_bins_per_update in a FOLLOW-ON
      run -- deliberately not changed in this one, to keep a single variable.
