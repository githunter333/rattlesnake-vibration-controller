-------------------------------------------------------------------------------
WHAT CHANGED IN THE CODE, AND WHAT DID NOT
-------------------------------------------------------------------------------
Every behaviour change from this week is now OPT-IN and off by default
(commit 45d417a3). Verified against the code as it stood at 2fb800a0, at
default parameters:

    match_trace_pseudoinverse, buzz_control, pseudoinverse_control
        cycle 2 onward identical to 1e-13 or exactly 0
    optimal_diagonal_control                 cycles 2-3 exactly 0
    optimal_diagonal_control_fast            bit-identical, 0.0e+00
    match_trace_pseudoinverse_pi             startup cap only

Turned back OFF by default: the dB error objective on both optimal-diagonal
laws (with it, drive_rcond and the IRLS passes are inert); the per-cycle
running ceiling on pseudoinverse_control and buzz_control; the live-FRF
drive-shape refresh on the match_trace pair.

KEPT ON, deliberately:

  THE STARTUP LEVEL CAP, -9 dB, on every law, with both its bugs fixed. It had
  compared tr(specification) against tr(DRIVE) -- not dimensionless -- and the
  coherence cap ran after it and lifted the level back through the ceiling.
  This is the one intended difference from runs 03/05/07.

  THE FAST LAW'S FRF-CHANGE GATE, now on relative Frobenius change against
  frf_update_threshold rather than bit equality. This is why run 21 is not a
  repeat: with the update ON and the old gate, H was never bit-identical, every
  bin fell through to the SDP, and runs 05 and 06 were the BASE law under the
  fast law's name. The factored path has never actually been tested.

The coherence cap is available on every law and is ON (0.95) in all three
profiles. On optimal_diagonal_control_fast it governs the SDP fallback only --
the factored path is unconstrained by construction. That is the intended
exception, not an oversight.

  THIS IS THE ONE THAT IS NOT A REPEAT. Run 05 scored 5.64 dB and was, we now
  know, the base SDP law. With the gate fixed the factored Burer-Monteiro path
  should actually engage.

  WATCH THE PER-CYCLE TIME. The factored solve measured 2.6 ms/bin against the
  SDP's 65 ms/bin offline, so a 20-bin cycle should be roughly 150 ms rather
  than about 1.3 s. If it still feels like run 05, the path still is not
  engaging and that is the finding.

  EXPECT SOME "FRF moved ... safe SDP path this call" LINES. With the update on
  the live FRF does move, and any cycle where it moves more than
  frf_update_threshold (0.05) correctly demotes every bin. A burst early then
  fewer is the healthy pattern; nothing but demotions means the live estimate
  never settles.

  The interesting comparison is run 21 against run 03/19, NOT against run 05 --
  run 05 and run 03 were the same law.
