WHY.  Run 01 was taken 2026-09-12 and is the stalest row on the board.  Since then

RUN 01 SCORED  rms 8.22, 59.8% of lines outside +/-3 dB, level +0.09, max 7.24 V,
drive 108.1 V^2, easy six 5.85 -- the worst of the four key laws by a wide margin.

near run 01, the law is simply weak on this plant and that is the finding.  If it moves
a lot, the 09-17 fixes mattered more for this law than for the others and that is a
different finding.

numbers are not comparable.  Run 01 and the comparison table are the plain one.

RUN 34 -- optimal_diagonal_control, cap 0.95, FRF update ON    (repeat of run 19)
-------------------------------------------------------------------------------
Profile : profile_03_optdiag_capon.xlsx
Script  : control_laws/optimal_diagonal_control.py   Function: optimal_diagonal_control
Params  : 1e-6,0.05,20,1.0,0.95               Update System ID During Control : Y

  SAVE AS  run34_optdiag_capon_guards_{sysid,spec,stream}.nc4

WHY.  This is the ONLY cheap way to see the two live-FRF guards run on a law other than
optimal_diagonal_control_fast.  Class hierarchy, checked rather than assumed:

    optimal_diagonal_control                          <- guards live here
    optimal_diagonal_control_fast(optimal_diagonal_control)   inherits
    octave_band_switching_control(optimal_diagonal_control)   inherits
    match_diagonal_congruence                         standalone, does NOT inherit
    match_trace_pseudoinverse                         a function, does NOT inherit

Run 19 (09-18 17:28) predates commit 7dbd1d5e, so it ran without them.

NOTE  profile_03 sets frf_update_threshold explicitly to 0.05, so the default change to
0.5 does NOT apply here.  At 0.05 expect the drift step to claim its full half-budget
every call (cum_frf_updates climbing by 10) exactly as it did in run 19 -- that is the
profile's setting, not a regression.

EXPECTED, from runs 03 and 19 which agree closely:
  rms 5.62-5.68, 19.1% outside +/-3 dB, level +0.1 to +0.2, max V ~4.4,
  drive ~67 V^2, easy six 2.44-2.50.
A third point in that band confirms the benchmark is stable across three code
generations.

WHAT WOULD BE A PROBLEM:  the guards firing repeatedly in band.  On run 32 they fired
three times in 281 calls, all during the startup transient.  Anything beyond that here
means the guards are too tight for a law whose scheduler behaves differently, and the
limit needs revisiting before this goes any further.
